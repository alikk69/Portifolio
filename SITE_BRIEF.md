## 2. Design system (verified against current `style.css` `:root`)

**This is NOT "The Ledger" (warm paper/serif) described early in PROJECT_NOTES.md — that was replaced in an earlier round.** Current system: clean neutral grayscale + one sharp accent.

--paper-panel: #eef0f3;    --paper-panel-strong: #e2e5ea;

--ink: #101216;   --ink-dim: #565b66;   --ink-faint: #686c75;

## 4. Architecture notes that matter

- **GSAP pins must be created together, in one shared block.** There's a documented, previously-real bug: creating `ScrollTrigger.create({pin:true})` calls in separate places in the script left earlier pins with stale start/end positions, because each call computes them against the document height *at that instant*, and a later pin's spacer insertion shifts the page height out from under an earlier one. The Achievements pin lives in one `ScrollTrigger.matchMedia()` block for exactly this reason. If anything else on the site ever needs a GSAP pin, it must go in that same block, not a new standalone `ScrollTrigger.create` elsewhere.
- **`position: fixed`/`sticky` breaks under a transformed ancestor.** Any non-`none` CSS `transform` on an ancestor creates a new containing block for `position: fixed` descendants, silently repositioning them relative to that ancestor instead of the viewport. This bit both the achievement modal (fixed via `.reveal.in-view { transform: none }` — not `translateY(0)`, which is *not* the same thing for this purpose) and the credit card's `position: sticky` reveal (bit by `#contact`'s own entrance-reveal transform). If something with `fixed`/`sticky` positioning starts behaving strangely — moving with scroll when it shouldn't, or vice versa — check every ancestor's `transform` first. **`filter` (any value other than the literal keyword `none` — `blur(0px)` counts as non-`none`) creates the identical containing block, undocumented anywhere but here.** `.reveal.in-view`, `.hero-inner.is-revealed`, and `scrollReveal()`'s GSAP tweens all resolve `filter` to literal `none`/a stripped inline style at rest for exactly this reason — never leave a settled entrance animation at `blur(0px)`, it looks like "off" and isn't.
- **A `position:fixed` descendant is still trapped inside an ancestor's stacking context for z-index purposes, even though its layout escapes to the viewport.** This is the same family of bug as the transform/containing-block issue above, but for *stacking* rather than *position*. `#mobileNav` — the fixed, viewport-covering hit area behind the mobile nav's dropdown card (`.mobile-nav-panel`, the actual visible card, is a child of it — see §3 for the current visual design; the DOM/stacking architecture described here hasn't changed across either version) — exists as a separate element and a sibling of `<main>`, **not** `#primaryNav` (the desktop inline row) reshaped into an overlay, specifically because `#primaryNav` lives inside `.navbar`, which is its own stacking context (`position: sticky` + explicit `z-index`). A `position:fixed` overlay nested in there would have its z-index evaluated *within* `.navbar`'s local stacking order, never able to compete against `.navbar` itself from outside it — meaning the logo and the hamburger/X toggle button would end up rendering *underneath* it, not above it, no matter what z-index it was given. As a sibling of `<main>` instead (both direct children of `.page`), `#mobileNav`'s `z-index: 95` correctly ranks just under `.navbar`'s `100` in their *shared* local stacking context, so the real navbar stays visibly pinned on top with no negative-z-index tricks needed. If you ever need another full-viewport overlay, check where in the DOM it actually needs to sit relative to whatever it must render above or below — don't assume nesting it "logically" (e.g., inside the element that triggers it) is stacking-neutral.
- **`html.nav-is-open` hides `.back-to-top` while the mobile nav is open, via a root class, not a CSS sibling selector.** `#mobileNav` (inside `.page`) and `.back-to-top` (a sibling of `.page`, outside it) aren't adjacent in the DOM, and `.back-to-top`'s effective stacking rank when compared against a *true* top-level element like a hypothetical outsider is capped by `.page`'s own low z-index regardless of what `#mobileNav`'s own z-index says internally — the same containment lesson as above, in the other direction. Toggling a class on `<html>` in script.js and keying off it in CSS sidesteps needing DOM adjacency or a correct cross-context z-index comparison at all.
- **`overflow: hidden` breaks `position: sticky` in descendants.** `#contact` had this for a decorative glow's clipping and it silently broke the card's sticky reveal. Removed. Don't re-add `overflow: hidden` to any section that contains a `position: sticky` element.
- **`mix-blend-mode` on the card's shine layer caused a full black-out** on some GPUs, inside the sticky + nested-transform stack. The shine uses plain `opacity` now — never reintroduce a blend mode there.
- **The readability scrim (`.has-skyline .page::before`) is load-bearing, not decoration.** `#experience`, `#achievements` and the hero are transparent, so their text sits directly on the WebGL skyline — and the lanes span the full viewport width, so a near-field vermillion candle really does pass behind the content column. Measured against that worst case, body copy is **1.26:1** with no scrim and **5.52:1** with it. The `0.86` centre alpha is the tuned value; lowering it for a bolder skyline costs roughly 0.07 of contrast ratio per 0.02 of alpha, and below ~0.84 the small mono labels drop under AA. It's gated on the `has-skyline` class that script.js adds only when the renderer actually paints, so mobile/no-WebGL keep the untouched flat gradient.
- **Three widgets use a roving tabindex** (`.config-option` radiogroups, `.trade-tab` tablist, `.career-node` tablist): only the selected item has `tabIndex 0`, the rest `-1`, with arrow/Home/End handlers moving between them. `showCareerPanel()` and `showSector()` maintain it, and there are explicit initialisers for the page-load state. If you add or re-render items in any of those groups, the tabindex has to be re-synced or the group becomes unreachable by keyboard.
- **`.ach-card` is a `<div>`, and the real control is `.ach-card-btn` stretched over it via `::after { inset: 0 }`.** It was a `<button>` wrapping an `<h3>` and two `<p>`s, which is invalid (button takes phrasing content only) and flattened the card into one run-on accessible name. Consequences to preserve: `.ach-card::after` (the ✓ badge) **must** keep `pointer-events: none` or it re-creates a dead click zone in the corner; the focus ring is drawn on the card via `:has(.ach-card-btn:focus-visible)`; and the modal's click handler binds to `.ach-card-btn`, while GSAP's pinned journey still targets `.ach-card`.
- **`--line-ui` vs `--line`/`--line-strong`.** The lighter two are for decorative rules and dividers. `--line-ui` (0.5 alpha, clears 3:1 per WCAG 1.4.11) is for the borders of actual controls — buttons, tabs, option pills, nav toggle, zoom buttons, modal close. Don't collapse them back into one token; the light ones fail 1.4.11 on controls and the dark one is too heavy for dividers.
- **Pagination dots are 44×44 `<button>`s with `gap: 0`, the visible dot drawn by `::before`.** They were 6px `<span>`s with click handlers inside `aria-hidden` containers, each given a `-19px ::after` hit area — a 44px target on a 12.8px pitch, so targets overlapped ~70% and the later sibling swallowed its neighbours' taps. The zero gap is deliberate: it's what makes the targets tile instead of overlap.
- **The site-wide entrance motion (`.reveal` in CSS, `scrollReveal()` in script.js, `.hero-inner`) is a scale+blur+translateY "settling into focus," not a plain fade — and `filter` carries the exact same fixed/sticky-breaking hazard `transform` does, undocumented anywhere outside this file and the inline comments.** Per spec, ANY `filter` value other than the literal keyword `none` — including `blur(0px)`, which looks like "off" — creates a new containing block for `position:fixed`/`sticky` descendants, identically to a non-`none` `transform`. `#contact` (wraps the sticky credit card) and `#achievements` (wraps the fixed modal) both use `.reveal` directly, so this isn't hypothetical. The rule holding it safe: `.reveal.in-view` and `.hero-inner.is-revealed` must resolve to the literal keywords `transform: none` and `filter: none` at rest — verified by reading `getComputedStyle` after the transition settles, not by eyeballing it. The GSAP side can't just declare a keyword the way CSS can (GSAP leaves whatever numeric value it tweened to, e.g. `blur(0px)`, sitting as an inline style) — `scrollReveal()` handles this with an `onComplete: () => gsap.set(el, { clearProps: "filter" })`, which strips the inline style entirely rather than hoping a zeroed value counts as none. If you add scale/blur/filter to any OTHER entrance animation on this site, especially near `#contact` or `#achievements`, it needs the same discipline.
- **Reduced motion has to force `filter: none !important` too, not just `opacity`/`transform`.** `.reveal.in-view`'s `filter: none` only applies once an element has actually scrolled into view and the IntersectionObserver adds `.in-view` — but the `@media (prefers-reduced-motion: reduce)` block force-shows everything (`opacity: 1 !important`) immediately, including content below the fold that hasn't been observed yet. Without also forcing `filter: none !important` in that same block, reduced-motion users would see below-the-fold sections rendered fully opaque but still blurred until they scrolled far enough for the observer to actually reach them — visible but illegible, which defeats the entire point of reduced motion. This shipped as a caught-before-verification bug in the same pass that added the blur; if you extend the motion system further, re-check this interaction.
- **Mobile's swipeable career/experience row (`.career-panel`) locks its own height to whichever card is currently showing, via `syncCareerPanelHeight()` in script.js.** Without it, the flex row sizes to its TALLEST child regardless of `align-items` (a flex line's cross-axis size is set by the tallest item no matter how children are aligned within it) — every shorter role sat inside a card-shaped box padded out with up to ~300px of blank paper below its own text (measured: Poly's two-sentence blurb inside a box sized for Nadher Media's three paragraphs + two stat chips). The fix needs BOTH pieces together: `align-items: flex-start` (mobile media query) so each item's own `scrollHeight` reports its true content height instead of the stretched one, and the JS syncing the container's actual `height` to match whichever item has `.is-active` — `align-items` alone doesn't shrink the visible card, since the container's own height is unaffected by it. Runs on every `showCareerPanel()` call (swipe, chip tap, dot tap) plus once on load and on resize; **the resize path actively clears the inline height (`.style.height = ""`) rather than merely skipping it above 820px** — otherwise crossing back to desktop width would leave the panel stuck at a stale mobile pixel height instead of returning to its normal auto-sized, single-item-shown layout.
- **`scrollReveal()`** (script.js) is the shared "fade/slide in once, on scroll" helper used almost everywhere. Its default is `from: {opacity:0, y:50}` → `to: {opacity:1, y:0}`; passing a custom `to` without an explicit `y` silently leaves the default `y:0` — that's usually fine, but if you ever pass a *non-zero* target position, you must include it explicitly in `to`, or it'll compute against a wrong default. This exact class of bug (a missing `to.y`) has shipped at least twice on this site (education items once, the card's slot once).

## 5. The credit card — history and current state

This went through **9 distinct rounds** (see PROJECT_NOTES.md rounds 25–34 for full blow-by-blow). Do not restart from scratch without reading at least the summary below — most of the obvious-looking approaches have already been tried and failed for specific, documented reasons.

**Current architecture** (as of round 34): a tall `.cc-scroll` spacer (150vh) containing a `.cc-sticky` frame (`position: sticky; top:0; height:100vh`) that holds the card+wallet centered in the viewport while the spacer scrolls behind it. The card's reveal progress is computed directly from scroll position every frame (`-rect.top / (scrollHeight - viewportHeight)`, clamped 0–1) — **not** GSAP-scrubbed, **not** pinned, **not** a one-shot trigger. This is deliberate and load-bearing:
- Because it's a *pure function* of scroll position with no animation state, it structurally cannot get stuck revealed, and reverses correctly every time you scroll back up — several earlier one-shot-trigger versions latched open permanently.
- Because the card only moves while `.cc-sticky` is pinned, and by that point the heading/intro above have already scrolled off, it structurally cannot cover text — several earlier versions needed careful pixel-margin tuning to avoid this and kept failing by a few pixels at some viewport width.
- A GSAP-pinned/scrubbed version was tried (matching a supplied design spec exactly) and worked correctly but read as "laggy" — scrub's catch-up smoothing lags real scroll input. The current version is native-scroll-driven with no smoothing lag.
- **`cardMech(p)`'s tail (the `p >= 0.75` branch) now has a slight spring overshoot** — an easeOutBack curve (`c1 = 3`, ~4.5% peak overshoot on `mech`, at `p≈0.876`) instead of a purely decelerating one, added for "card motion" polish on both mobile and desktop (tilt is mousemove-only and does nothing on touch, so this — being scroll-position-driven — is the one motion upgrade that actually reaches both). **`cardMech(1)` still resolves to exactly `1`, bit-for-bit** — verified via `card.style.transform` at `p=1`: `y=-172.00`, `scale=1.0000`, matching `CARD_REVEAL_Y` precisely. This is why it's safe: the overshoot only ever pushes `y` *more negative* than `CARD_REVEAL_Y` (further from the wallet), never back toward it, so it structurally can't reintroduce the pocket-clearance bugs above — but if `CARD_TUCK_Y`/`CARD_REVEAL_Y` or the wallet geometry ever change, re-verify `cardMech(1) === 1` stayed exact before assuming the rest state is still correct.

**Key tuned constants in script.js** (`CARD_TUCK_Y`, `CARD_REVEAL_Y`) and matching CSS (`.cc-wrap` stage height, `.cc-wallet` height, `.credit-card`'s `bottom` offset) are **not arbitrary** — they were derived from real measured geometry (the wallet and card's bottom edges are both anchored to the same parent's bottom, so clearance is independent of card width) and then adjusted again when the card was resized. If you resize the card or wallet, re-verify clearance at both ends of the reveal, not just visually — a few pixels of overlap is easy to miss by eye and was shipped more than once.

**Also currently present:** hover tilt (`mousemove` → ±14° `rotateX`/`rotateY`, independent of the scroll-driven transform, composed into the same transform string), a shine sweep (plain opacity, see §4), a `.cc-sticky::before`/`::after` backdrop (blueprint grid + warm glow) added specifically because an earlier version left the card floating alone in a blank viewport — don't strip the backdrop without adding something else in its place.

**On testing this specific section:** if you're using a headless/automated browser tool to verify it, be aware that some tools freeze `requestAnimationFrame` and CSS transitions when they report the tab as backgrounded/hidden, which can make working code look broken in testing (GSAP tweens stuck at time 0, CSS transitions never progressing). Also, `Element.getAnimations()` does not report GSAP-driven tweens at all — only native CSS transitions/WAAPI. If a scroll-driven reveal looks stuck during testing, force-recompute from real scroll position and check computed styles directly, rather than trusting animation-inspection APIs.
